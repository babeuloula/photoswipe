# CLAUDE.md — PhotoSwipe

> **À maintenir à jour.** Toute PR qui change une commande, une convention, la structure des modules ou le processus de travail met à jour ce fichier dans la même PR.

Application Android (Kotlin + Jetpack Compose) qui fait revoir chaque jour les photos et vidéos prises le même jour lors des années précédentes. Tri par swipe : gauche = marquer pour suppression, droite = garder, haut = menu favori / partage.

## Règles permanentes (résumé du SPEC §0)
- Le code est en anglais. Les commentaires et la KDoc sont en français.
- Aucune chaîne en dur dans l'UI : `values/strings.xml` en anglais, `values-fr/` en français. `MissingTranslation` est une erreur.
- `:domain` est du Kotlin JVM pur : ni Android, ni Room, ni Compose. Les dépendances vont toujours **vers** `:domain`.
- Principes SOLID et KISS, injection par constructeur (Hilt + KSP), aucun singleton statique.
- Aucune permission `INTERNET`. L'application est 100 % locale.
- Chaque ticket est livré avec ses tests. Rien n'est terminé sans tests verts, en local comme en CI.
- Aucune nouvelle bibliothèque sans une justification d'une ligne dans `docs/architecture.md` ; une dépendance ou une police embarquée dans l'APK s'ajoute aussi à `OPEN_SOURCE_LIBRARIES` (`ui/licenses`), avec sa licence (`OpenSourceLicense`).
- Versions : vérifier les dernières versions stables sur les sources officielles (Google Maven, Maven Central, services.gradle.org), pas de mémoire.

## Commandes
Prérequis : JDK 17 et le SDK Android (`local.properties` contient `sdk.dir`, ce fichier n'est pas commité).

```bash
# En local sur la machine de Jérémy : le JBR d'Android Studio est en version 25, on force le JDK 17
export JAVA_HOME=/opt/homebrew/opt/openjdk@17

./gradlew test            # tests unitaires de tous les modules + tests des conventions build-logic
./gradlew quality         # ktlint + detekt + Android Lint sur tous les modules (bloquant)
./gradlew ktlintFormat    # corrige automatiquement la mise en forme
./gradlew assembleDebug   # APK debug dans app/build/outputs/apk/debug/, installable par-dessus le précédent (clé app/debug.keystore, versionCode = nombre de commits, versionName = dernier tag vX.Y.Z)
./gradlew :app:bundleRelease   # AAB release, signé si keystore.properties (hors Git) pointe la clé d'upload ; voir docs/store/README.md
# Release officielle : Actions → Release → Run workflow (vX.Y.Z), CI de main verte exigée : branche release/vX.Y.Z avec les notes F-Droid, tag, AAB, APK signés et version.properties joints (secrets PHOTOSWIPE_UPLOAD_*), PR ouverte par PHOTOSWIPE_RELEASE_TOKEN et mergée seule (auto-merge, merge commit)
git tag v1.2.0-dev.3 && git push origin v1.2.0-dev.3   # tag à la main : seulement vX.Y.Z-dev.N, pré-version avec l'APK debug ; tout autre tag est supprimé
./gradlew test quality assembleDebug   # ce que lance le job obligatoire de la CI
./gradlew connectedDebugAndroidTest   # tests instrumentés (src/androidTest), émulateur démarré ; second job de la CI
scripts/seed-emulator.sh [--remove]   # pousse (ou retire) des photos datées par EXIF sur l'émulateur (adb, python3, ffmpeg) : vraies photos de Jérémy dans `scripts/fixtures/photos`, sans métadonnées, réécrites en EXIF à chaque envoi (portrait, paysage, carré, panorama), rafales aujourd'hui et à J-4, une seule photo à J-2
scripts/fdroid-changelog.sh vX.Y.Z    # lancé par le workflow Release : notes de version F-Droid (changelogs/default.txt) tirées des notes générées par GitHub (gh)
python3 -m unittest discover -s scripts && shellcheck scripts/*.sh   # tests des scripts, lancés aussi par la CI
node --test pages/crash/*.test.mjs   # tests de la page d'envoi des rapports de plantage, lancés aussi par la CI
```

## Structure
- `pages/` : pages web publiées sur GitHub Pages par `.github/workflows/pages.yml` (depuis `main`, polices de l'app copiées à la publication) : `crash/` (<https://babeuloula.github.io/photoswipe/crash/>) affiche le rapport de plantage reçu dans le fragment de l'URL et ne l'envoie à GlitchTip (`glitchtip.babeuloula.fr`, projet PhotoSwipe, DSN public dans `crash.js`) qu'à la demande ; tests `crash.test.mjs` (Node), ADR 0033.
- `scripts/` : outils de développement hors Gradle (`seed-emulator.sh`, `seed_photos.py` et ses tests `test_seed_photos.py`, photos de test de Jérémy dans `fixtures/photos` (PS-145, remplacent celles d'Unsplash de PS-143), sans métadonnées ; `fdroid-changelog.sh`, `fdroid_changelog.py` et ses tests `test_fdroid_changelog.py`, PS-129 ; `deprecation_report.py` et ses tests `test_deprecation_report.py`, rapport des dépréciations de la CI, PS-132 ; en Python de la bibliothèque standard).
- `:app` : UI, navigation, assemblage DI (modules Hilt dans le package `di`), point d'entrée Android (`fr.babeuloula.photoswipe`). Les demandes de lancement (rappel, liens `photoswipe://`, raccourcis) : package `link` (`LaunchRequest`, `DeepLinks`, `LaunchRequestResolver`, ADR 0038), schéma documenté dans le README. Les plantages : `crash` (`CrashReportHandler`, installé par `PhotoSwipeApplication`, enregistre le rapport au format Sentry de `CrashReportFormatter` dans `CrashReportStore`, fourni par `di/CrashReportModule`) puis `ui/crash` (`CrashReportPrompt` à la racine de `PhotoSwipeApp` : au lancement suivant, « Voir et envoyer » ouvre la page d'envoi par `CrashReportLink`, rapport gzip + Base64 URL dans le fragment, ou « Ignorer » ; effacé dans les deux cas), sans permission `INTERNET` (ADR 0033). L'application est verrouillée en portrait (`screenOrientation="portrait"` dans le manifeste, décision de Jérémy), sauf le plein écran vidéo et la photo en grand de la pile, qui libèrent l'orientation le temps de leur affichage : `RotationPolicy` (`ui/common/RotationRequests.kt`, posée par `MainActivity`) met `FULL_USER` tant qu'un écran appelle `AllowRotation`, sinon le portrait (ADR 0028, PS-126) ; sur grand écran (largeur minimale ≥ 600 dp), Android 16+ ignore ce verrou pour notre cible SDK : les écrans s'adaptent alors à la fenêtre via `currentWindowLayout()` (`ui/common/WindowLayout.kt`, Material 3 Adaptive) : deux volets (accueil : liste à gauche, détail du jour à droite ; pile avec boutons en colonne) en largeur étendue ou en paysage, contenu centré (`CenteredContent`) en largeur moyenne. Chaque écran vit dans son package `ui/<écran>` : `XxxScreen` sans état (aperçus, tests UI), relié à son `XxxViewModel` (`@HiltViewModel`, `hiltViewModel()`, par un `XxxRoute` qui exécute les effets), qui expose un `XxxUiState` en `StateFlow`, reçoit des `XxxEvent` et émet des `XxxEffect` ponctuels (canal lu une fois). L'accès aux médias passe par `MediaAccessGate`, qui entoure le `NavHost` et n'affiche la navigation qu'avec la permission ; au premier lancement, `TutorialGate` (`ui/tutorial`) montre d'abord le tutoriel (ADR 0027). Navigation : routes `@Serializable` dans `ui/navigation/Routes.kt` (types simples seulement, par exemple `DeckRoute(epochDay)`), graphe dans `PhotoSwipeNavHost` ; chaque écran garde sa route, dont `TutorialRoute` pour le tutoriel revu depuis les réglages (ADR 0014 ; les coquilles `ShellScreen` ont toutes été remplacées). Les images passent par Coil 3 : l'`ImageLoader` vient de Hilt (`di/ImageModule`) et se lit par `LocalImageLoader` (`ui/common`), fourni par `MainActivity` ; un test qui remplace le contenu de l'activité le refournit (ADR 0016). Le thème Material 3 vit dans `ui/theme` (`PhotoSwipeTheme`) : les écrans lisent couleurs, typo, formes et mouvement (`MaterialTheme.motion`, ressorts Expressive) via `MaterialTheme`, jamais en dur ; les couleurs hors rôles Material 3 (vert « garder » et bleu « favori » des indicateurs) sont des couleurs du thème, avec leurs conteneurs, lues par `MaterialTheme.swipeColors` ; ce qui est posé sur une photo (repère, pastilles) utilise les rôles fixes (`primaryFixed`, `onPrimaryFixed`…). Palette « planche-contact », graine ambre #8A6A1E, toujours appliquée : pas de couleurs dynamiques Material You (ADR 0025, PS-102). Le thème clair ou sombre suit le choix des réglages (`ThemeMode` de `SettingsRepository`, celui du téléphone par défaut) : `MainActivity` l'observe, le lit une fois avant d'afficher l'interface, et accorde les barres système (`enableEdgeToEdge` avec `SystemBarStyle.auto`) ; `ThemeMode.isDark` (`ui/theme/AppTheme.kt`), ADR 0022.
- `:data` : implémentations Android des ports du domaine : MediaStore, Room, DataStore, WorkManager (`fr.babeuloula.photoswipe.data`). Ses modules Hilt vivent dans `data/di` (`PortsModule`, qui lie aussi `MediaActionRequestFactory` à `MediaStoreActionRequestFactory` ; `StorageModule`, `DispatchersModule` avec `@IoDispatcher`) : un port se lie là, sauf `MediaSource`, lié dans `:app` par variante (`src/release` : MediaStore ; `src/debug` : `SwitchableMediaSource` et données de démo, ADR 0015). La base Room vit dans `database` (`PhotoSwipeDatabase`, `ReviewEntryEntity`, `ReviewEntryDao`, journal des décisions `DecisionRecordEntity` / `DecisionJournalDao`, ADR 0019 ; historique des suppressions confirmées `ConfirmedDeletionEntity` / `ConfirmedDeletionDao`, lu par `RoomDeletionHistory` (`data/deletion`), ADR 0034 ; activité de tri par jour `DailyActivityEntity` / `DailyActivityDao`, lue par `RoomActivityHistory` (`data/activity`), les médias gardés y étant comptés par `DecisionJournalDao` dans la transaction de la décision, ADR 0037) ; son schéma est exporté dans `data/schemas/` et commité : changer l'entité impose une nouvelle version et une migration (ADR 0013) ; les migrations manuelles vivent dans `database/Migrations.kt` et s'ajoutent au `databaseBuilder` de `StorageModule` (version 5 : 3 → 4 automatique pour `confirmed_deletion`, 4 → 5 automatique pour `daily_activity`, ADR 0026, 0034 et 0037). Le jeu source `data/src/debug` (seeder MediaStore, package `seed`, ADR 0020) n'existe qu'en debug ; ses tests JVM vont dans `data/src/testDebug`.
- `:domain` : modèles (`model`), services purs (`service`), ports (`port`, uniquement des interfaces aux appels `suspend`, dont `DecisionJournal` pour l'undo persistant (ADR 0019) et `DeletionHistory` pour les suppressions confirmées des 7 derniers jours (ADR 0034) et `ActivityHistory` pour l'activité de tri par jour (ADR 0037) ; `Flow` seulement pour une lecture observée, comme `ReviewRepository.observeEntries` ou `SettingsRepository.observeReminderSettings`, ADR 0007 et 0008), use cases (`usecase`, un par intention avec `operator fun invoke`), en Kotlin JVM pur (`fr.babeuloula.photoswipe.domain`). Fixtures de test partagées dans `src/testFixtures` (package `fixtures` : `aMediaItem()`, `aReviewEntry()`, `FakeMediaSource`, `FakeReviewRepository`, `FakeDecisionJournal` (écrit dans un `FakeReviewRepository`), `FakeDeletionHistory`, `FakeActivityHistory`, `aConfirmedDeletion()`, `FakeSettingsRepository`, `FakeReminderScheduler`, `FakeReminderNotifier`, `aDecisionRecord()`, `FakeMediaActionRequestFactory`, `FakeUsageStatisticsRepository`, `FixedClock`), consommées par `:data` et `:app` via `testImplementation(testFixtures(project(":domain")))`.
- `:architecture-tests` : tests d'architecture Konsist seulement (ADR 0005). `:domain` n'importe ni `android.*`, ni `androidx.*`, ni `com.google.android.*`, ni rien du projet hors `…domain` ; `…domain.port` ne déclare que des interfaces ; `:app` n'importe `…data` que depuis son package `di`. Chaque règle est testée sur des fixtures (`src/test/resources/fixtures`). Un nouveau module ou une nouvelle règle de dépendance s'ajoute ici, et ses sources dans les entrées de la tâche `test` du module.
- `build-logic/` (build inclus) : plugins de convention `photoswipe.android.application`, `photoswipe.android.library`, `photoswipe.jvm.library`, `photoswipe.android.hilt` (KSP + Hilt), `photoswipe.android.compose` (compilateur Compose + BOM), `photoswipe.android.room` (KSP + Room, schémas exportés dans `schemas/`) et `photoswipe.android.robolectric` (Robolectric hors ligne), ces quatre derniers à appliquer après une convention Android, et `photoswipe.quality` (ktlint + detekt + tâche `quality`), appliqué d'office par les trois conventions de module (ADR 0003). Les valeurs partagées (SDK, JVM) sont dans `ProjectConfig`. KSP s'applique par `applyKsp()` (`Ksp.kt`) : ses tâches passent une à une dans tout le build (service `KspOneAtATime`), ne passent pas par le cache de build et `ksp.incremental=false` (`gradle.properties`), car il perdait des sources générées (`Hilt_*`, modules de `src/debug`), ADR 0021. Un module applique sa convention et ne déclare que ce qui lui est propre (namespace, dépendances). Toute nouvelle configuration commune (Compose, Hilt, qualité) devient un plugin de convention (ADR 0001).
- i18n : `values/` (anglais) et `values-fr/`, un fichier par type (`strings.xml`, `plurals.xml`). La langue de l'app se choisit dans le réglage de langue par application d'Android 13+, ouvert depuis les réglages (`locale/AppLanguage.kt`). Une nouvelle langue `values-xx` s'ajoute aussi dans `res/xml/locales_config.xml` ; `LocalizationTest` vérifie la parité des clés et la déclaration des langues.
- Qualité : style ktlint `ktlint_official` (`.editorconfig`), règles detekt ajustées et justifiées dans `config/detekt/detekt.yml` (dont la KDoc obligatoire sur l'API publique, `UndocumentedPublic*` ; detekt ne lit que `src/main`, `src/test` et `src/testFixtures`), Android Lint avec `MissingTranslation` en erreur. Les dépréciations ne bloquent pas : la CI les relève (`scripts/deprecation_report.py`, compilation Kotlin hors build cache par `.github/ci/kotlin-warnings.init.gradle.kts`) en avertissements et en un commentaire de PR mis à jour à chaque push (PS-132).
- Versions : `gradle/libs.versions.toml`, sans aucune version en dur ailleurs. CI : `.github/workflows/ci.yml` ; `.github/workflows/release.yml` (lancé à la main avec `vX.Y.Z`, CI de `main` verte exigée : release signée par la clé d'upload des secrets, notes F-Droid, PR de release ouverte par `PHOTOSWIPE_RELEASE_TOKEN` et mergée par auto-merge, AAB, APK et `version.properties` joints ; tag poussé à la main : seulement `vX.Y.Z-dev.N`, APK debug en pré-version ; PS-115, PS-130, ADR 0032) ; la PR de release porte le label `release`, exclu des notes générées par GitHub (`.github/release.yml`) : mergée après la pose du tag, elle n'apparaît plus dans les notes de la release suivante (PS-135 de Notion, testé par `scripts/test_release_notes_config.py`) ; les branches `release/v*` ne peuvent pas être supprimées (ruleset « release branches: no deletion ») ; son job « Quality, unit tests and debug build » est un check obligatoire du ruleset de `main` (ADR 0004), le renommer impose de mettre à jour le ruleset ; le job « Instrumented tests (emulator) » lance les tests instrumentés.

## Tests
- `:domain` et `:architecture-tests` : JUnit Jupiter (JUnit 6). Les fonctions `suspend` se testent dans `runTest` (kotlinx-coroutines-test). Un `Flow` se teste avec `first()`, ou en collectant dans une liste depuis `backgroundScope` avec `UnconfinedTestDispatcher(testScheduler)`. Turbine, prévu par la SPEC §11, n'est pas encore ajouté (ADR 0008).
- Données de test : les builders, fakes et `FixedClock` de `:domain` (`testFixtures`) plutôt que des objets construits à la main ; un nouveau fake respecte le contrat de son port et est lui-même testé.
- Modules Android (`:app`, `:data`) : JUnit 4, en attendant une décision ADR sur JUnit 5/6 côté Android.
- Tests qui ont besoin d'Android ou de Hilt : Robolectric (convention `photoswipe.android.robolectric`, `robolectric.properties` à `sdk=34` dans chaque module) + `@HiltAndroidTest` (`HiltTestApplication`), sur l'API 34 (ADR 0002). Room se teste sur une base en mémoire (`Room.inMemoryDatabaseBuilder`). Robolectric tourne hors ligne : monter sa version impose de mettre à jour `robolectric-androidAll` dans le catalogue (sinon « Path is not a file »).
- Variantes : `src/debug` (outils développeur : données de démo, remise à zéro des décisions, entrée dans les réglages ; jamais en release) et `src/release`. Leurs tests vont dans `src/testDebug` et `src/testRelease` ; les tests unitaires release sont activés mais filtrés sur `src/testRelease` (`app/build.gradle.kts`).
- ViewModels : `MainDispatcherRule` (`app/src/test`) remplace `Dispatchers.Main` ; collecter un `StateFlow` avec `backgroundScope.launch(UnconfinedTestDispatcher(testScheduler))`. Use cases réels construits sur les fakes de `:domain`.
- Remplacer une liaison Hilt dans un test : `@UninstallModules(MediaSourceModule::class)` + `@BindValue @JvmField val mediaSource: MediaSource = FakeMediaSource(…)`.
- Un test qui démarre `MainActivity` sans `setContent` passe d'abord par le tutoriel (réglages vides) : pour commencer sur l'accès aux médias ou l'accueil, `@UninstallModules(TutorialModule::class)` et `@BindValue` de `ShouldShowTutorial` / `MarkTutorialSeen` sur un `FakeSettingsRepository(tutorialVersionSeen = Tutorial.CURRENT_VERSION)` (exemple : `MainActivityTest`).
- Tests Compose : `androidx.compose.ui.test.junit4.v2.createAndroidComposeRule<MainActivity>()` (les API v1 sont dépréciées). Pas de `createComposeRule()` : son activité hôte (`ui-test-manifest`) n'est pas visible des tests unitaires Robolectric ; pour lire des valeurs de thème, composer dans `Robolectric.buildActivity(ComponentActivity::class.java)`.
- Tests instrumentés (`src/androidTest`, `:data`) : `AndroidJUnit4`, mêmes noms de tests qu'ailleurs (les espaces sont acceptés par le DEX depuis l'API 30, sous notre `minSdk` 33). MediaStore réel : insérer des JPEG datés par EXIF (MediaStore recalcule `DATE_TAKEN`), attendre leur indexation (`MediaStoreIndexing.scanOwnMedia` puis `eventually`, PS-103) et les supprimer ; migrations Room avec `MigrationTestHelper`.
- Mesure du texte (nombre de lignes, `autoSize`) : annoter le test `@GraphicsMode(GraphicsMode.Mode.NATIVE)`, le mode par défaut de Robolectric ne mesure pas vraiment le texte (exemple : `SummaryScreenTest`).
- Accessibilité : un nouvel écran s'ajoute à `AccessibilityTest` ; la checklist manuelle (TalkBack, police à 200 %, contraste) est dans `docs/testing.md`.
- Les noms des tests sont en anglais et décrivent le comportement, par exemple `` `moves leap day media to February 28 on non-leap years` ``.

## Processus de travail
1. On travaille un ticket (PS-N) à la fois, dans l'ordre de l'epic. Chaque ticket a sa branche `ps-N-description` et sa PR vers `main`.
2. Avant de commiter, `./gradlew test quality assembleDebug` doit passer.
3. Les commits suivent Conventional Commits et citent le ticket, par exemple `feat(core): add multi-module skeleton (PS-1)`.
4. Chaque PR est assignée à `babeuloula` et porte :
   - un label `epic: N-nom` ;
   - un ou plusieurs labels `area: build|ci|quality|app|data|domain|i18n|testing` ;
   - un label de type : `enhancement`, `bug`, `documentation` ou `accessibility`.

   Lancer `gh label list` avant de créer un nouveau label.
5. **La CI est maintenue au fil du projet.** Tout nouveau check (ktlint, detekt, Konsist, tests instrumentés, nouveau module, etc.) est ajouté à `.github/workflows/ci.yml` dans la même PR. Une PR n'est prête que si son run CI est vert.
6. **La documentation est maintenue au fil du projet.** On met à jour `CLAUDE.md`, `docs/architecture.md`, `docs/beginners-guide.md` et `docs/testing.md` dès qu'un module, un dossier, un outil ou une commande change.
7. **Démo sur émulateur** : si le ticket a un effet visible, on lance l'émulateur (`~/Library/Android/sdk/emulator/emulator -avd Medium_Phone_API_37.0`), on installe l'app (`./gradlew installDebug`) et on donne à Jérémy la liste de ce qu'il faut tester et comment. Si le ticket n'a rien de visible, on le dit explicitement.
8. **Suivi Notion** : les tickets vivent dans le kanban Notion « Tickets de développement » (page PhotoSwipe). Le `Ticket ID` Notion (PS-N) fait foi pour la numérotation. Le statut avance au fil du travail :
   - « En cours » quand on commence le ticket ;
   - « En revue » à l'ouverture de la PR, avec les critères d'acceptation cochés et le lien de la PR ;
   - « Terminé » une fois la PR mergée.
9. Après avoir ouvert la PR, on s'arrête et on attend la revue avant le ticket suivant.
10. Ne rien faire qui dépasse le périmètre du ticket et de l'epic en cours.
